# Caller correlation keys

The API's v1 derivation helper produces a stable pseudonym for a validated issuer and a selected `sub` or `oid`. It does not select claims, load keys, or send or log the result. This change does not enable correlation in the host.

- **Provisioning:** Generate exactly 32 random bytes with a cryptographically secure generator. Keep them in an operator-managed secret source with least-privilege access. Supply the same key to replicas in one approved correlation scope; use separate keys for other scopes and deployments. Never reuse signing, continuation, data-protection, credential, or audit keys. The helper rejects absent, wrong-length, and all-zero keys, but cannot establish key entropy or replica consistency.
- **Rotation:** Stage the next key and coordinate a single-key cutover. Drain old-key traffic before reopening if consistency during the cutover is required. Different keys produce different values, even though the `v1.` prefix stays the same. Revoke old access according to retention policy. The future in-memory key owner must clear its writable key buffers when they are no longer needed. If a key is compromised, rotate it promptly: with that key, previously emitted IDs can be re-identified by testing candidate identities. Rotation does not undo that exposure.
- **Refusal and redaction:** An invalid key, unknown subject kind, or missing or invalid issuer or subject produces a fixed reason and no identifier. A future host must not enable required correlation with an invalid key or send a request requiring correlation when derivation fails. There is no fallback. Treat the value as pseudonymous, not anonymous and not an authorization input. Keep the value, tokens, claims, raw inputs, frames, key material, and key-source details out of ordinary logs, exception messages and payloads, traces, and metrics. Configure header and log redaction at both ends of the future hop: the federation and the receiving backend. Restrict access to and retention of any approved correlation records.
